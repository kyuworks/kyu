# Kyu 急

The company message bus: events, commands and durable workflow orchestration for every internal project, built on self-hosted [Hatchet](https://github.com/hatchet-dev/hatchet).

Kyu sounds like queue, and the kanji 急 (kyū) means urgent or express, as in express delivery. The kanji is the logo. A message is express: it is delivered promptly to the consumers that subscribed, and nowhere else.

## Install

`pnpm add @kyuworks/sdk` (it brings `@kyuworks/schemas` at the same version; add it too only if you import it directly). Both are public on npm with provenance from this repository.

pnpm 11 refuses a version younger than a day (`minimumReleaseAge`, default 1440 minutes). To take a new Kyu release the day it ships, add to your `pnpm-workspace.yaml`: `minimumReleaseAgeExclude: ['@kyuworks/*']`.

Apply the SDK's migrations with your own migration runner: every `*.sql` file in `MIGRATIONS_DIRECTORY` (exported by the SDK), in file-name order, each once. A released file never changes; a new version may add files, and the changelog in the GitHub release for the tag says which one a feature needs.

## Packages

| Package | Purpose |
| --- | --- |
| `@kyuworks/schemas` | The envelope contract, naming rules, schema adapters |
| `@kyuworks/sdk` | Publish through a transactional outbox, subscribe with Hatchet, run durable handlers, rate-limit a subscription in product units (per business tenant, correlation id or payload field), read a run's outcome by envelope id, read every run for one correlation id, cancel the runs for one envelope id, every run under one correlation id, every unsettled run for one business tenant or every unsettled run in the namespace, pause and resume a business tenant |

A process that only publishes needs no engine credentials. `createPublisher({ source })` returns
just `publish`, writes the outbox row inside the caller's transaction and never builds an engine
client, so a web API or a CLI needs only its own database. `createKyu({ hatchet, source })` is for
a process that also subscribes, runs a worker, starts the relay (normally its own process, one per
project) or reads run outcomes; those need `HATCHET_CLIENT_TOKEN`, and `createHatchetClient()`
throws "API token is required" the moment it is called without one.

A subscription's `name` must be lowercase letters, digits, `-` or `_`, starting with a letter.
`subscribe()` and `durable()` refuse anything else, because the engine lowercases the name when it
registers the workflow and `runs.forEnvelope()` would then report a name the caller never chose.

A subscription's `concurrency` key groups runs; `maxRuns` caps each group and `strategy` says what happens when a group is full. `'fifo'` and `'round-robin'` are the same engine strategy — runs queue in publish order inside a group, and groups take turns — so the name only records which one you are buying: `'fifo'` for a per-entity key such as `input.data.orderId`, `'round-robin'` for a key that groups a whole business tenant. `concurrency: { key: TENANT_CONCURRENCY_KEY, maxRuns: 1, strategy: 'round-robin' }` gives every business tenant one run at a time on that subscription. A tenant publishing five thousand messages cannot push a tenant publishing five to the back of the queue. `TENANT_CONCURRENCY_KEY` is `'input.tenantId'`, the tenant id on the envelope the relay pushes. This key requires every message on the subscription to carry a tenant id: an envelope with `tenantId: null` fails its run at the engine (`failed to parse step expression (input.tenantId)`), and a replay fails the same way, so use a different key or a constant for subscriptions that carry tenant-less messages. `'cancel_in_progress'` and `'cancel_newest'` still coalesce instead of queueing.

Run the relay on a small dedicated `pg.Pool` (the shop uses `max: 1`), not the application's pool and not a bare `pg.Client` (`kyu.startRelay({ db: pool, workerId })`). The relay never opens a transaction — a claim is held by the row's `claimed_by` stamp, not by the connection — so a pool is safe, and pg replaces a dropped connection on the next tick. `publish()` and `onceById()` still refuse a pool: their statements must land in the caller's transaction. Attach `pool.on('error', …)`, or a connection dropped while idle takes the process down. The relay, `publish()`, `onceById()` and tenant pause are tested through a transaction-mode PgBouncer ([`pooler.integration.test.ts`](packages/sdk/src/db/pooler.integration.test.ts)).

A relay handed a single `pg.Client` cannot recover: pg marks a client that lost its connection permanently unusable. The relay notices, stops polling, calls `onError` with a `RelayConnectionLostError` and rejects `relay.closed`. Exit non-zero on that rejection and let a supervisor restart the process. Rows the relay had claimed stay claimed until `staleClaimMs` passes, then another relay takes them over.

**Outbox retention.** `kyu_outbox` is a delivery buffer, not an event log or an audit trail ([ADR](docs/architecture/adr/20261002-the-outbox-is-not-the-audit-log.md)). The SDK never deletes a row on its own, and the relay never prunes. Run `pruneOutbox(pool)` once a day from your own scheduler: it deletes published, retired and cancelled rows older than 45 days (the prune floor), 1000 rows per statement, and returns `{ published, retired, cancelled }`. It never deletes a pending, scheduled or claimed row. A shorter `olderThanMs` throws a `KyuError` unless you also pass `allowBelowFloor: true`. Pass a longer one when your longest durable wait plus the engine's retention (30 days in production) is more than 45 days. For a job of your own, `prunePublished`, `pruneRetired` and `pruneCancelled` take an optional `limit`. Every call is one statement, so a pool or a transaction pooler is fine.

A row whose `envelope` column does not parse can never be shipped: the column is written once and never changed. The relay records the reason in `last_error`, and on the third such claim stamps `dead_at` and stops claiming the row, so it leaves the pending set instead of climbing `attempts` for ever. Retired rows appear on `onTick(result).retired` and in `SELECT … FROM kyu_outbox WHERE dead_at IS NOT NULL`, and `pruneRetired({ retiredBefore })` deletes them once they have been looked at. Rows that fail to push are not retired: the engine being down is temporary, and those keep retrying. A retired row is a message that will never be delivered, and a permanent gap in its key's order. An operator who fixes the envelope by hand revives the row with `UPDATE kyu_outbox SET dead_at = NULL, attempts = 0, last_error = NULL WHERE id = $1`, so the relay claims it again.

`publish(tx, definition, data, { tenantId, publishAt })` holds a message back until `publishAt`. The row is written in the caller's transaction like any other, so a rollback cancels it; the relay simply does not claim it until its time. The envelope id and `correlationId` are minted when `publish()` runs, not when the row ships, so a redelivered scheduled message carries the id the caller already has. A past `publishAt` is due at once, and an invalid `Date` throws. A scheduled message has no publish-order guarantee against messages published after it: it arrives at its own time. Consumers must apply migration `20260922022251_outbox_publish_at.sql` before deploying an SDK version that carries this feature.

A durable run cannot outlast its `executionTimeout`, which `durable()` sets to 24 hours when the caller does not: the engine cancels a run whose sleeps and waits pass it, mid-wait. `sleepFor` and `waitFor` are for waits inside that ceiling. Read the time inside a durable body with `ctx.now()`, not `Date.now()`: the body re-runs on every retry and replay, and `now()` returns what the first attempt read. For a longer wait, hand it off instead of sleeping: in one transaction, record where the run got to and publish the handler's own trigger message again with `publishAt` set to the wake time, computed from `ctx.now()`, and a field saying where to continue, then return. The run ends holding nothing, and the relay starts a fresh run at the wake time. [The shop example's `src/handlers/runWorkflow.ts`](https://github.com/kyuworks/shop-example/blob/main/src/handlers/runWorkflow.ts) does this for a workflow delay step of 60 seconds or more.

A durable run parked in `sleepFor`/`waitFor` reads as `running` in that outcome — the engine exposes no separate parked state. A run reads `completed` only once the engine has recorded both `startedAt` and `finishedAt`, and `failed` only once it has recorded `finishedAt`; a run caught in the gap between the terminal status and those timestamps reads `running` instead. The engine's run list can also keep an ended run as queued or running for good (`docs/proofs/2026-09-23-engine-run-list-stale-rows.md`), so for a run it has shown queued or running for 60 seconds or more, the SDK reads the engine's own run detail once — at most 100 such runs per call — and reports `completed` or `failed` when that says so, with no `finishedAt` if the list never recorded one. A failed run may have no `startedAt` at all, because it can end before any worker starts it.

`kyu.runs.forCorrelation(correlationId)` returns every run that shares one correlation id — a durable run and the command runs it published — oldest first, ordered by the engine's `createdAt` and then by run id. `forEnvelope` returns one message's runs newest first, because it answers what happened most recently; `forCorrelation` reads like a progress list, so it runs the other way. A run that is still `running` also carries `waiting` when it is parked: `{ kind: 'sleep', until }` for `sleepFor`, or `{ kind: 'message', name, match? }` for `waitFor`, where `match` is the `{ field, equals }` it is holding out for, and `{ kind: 'anyMessage', waits }` for `waitForAny`, one entry per name. The engine has no parked status, so `waiting` is what tells the two apart; it is a snapshot of the durable log at read time and can lag briefly after the wait is actually satisfied. A run that has finished, failed or been cancelled never carries one. Each parked run costs one extra engine read, and the durable log it reads is bounded at 5000 entries. A run parked by an SDK version older than this one, or one whose label this SDK cannot decode, reports the event `name` with no `match` rather than failing the whole read; it clears when that run ends.

`kyu.runs.cancelForEnvelope(envelopeId)` cancels every run the engine holds for one envelope id. `kyu.runs.cancelForCorrelation(correlationId)` cancels every run that shares one correlation id — a durable run and the command runs it published. Both return the runs they asked the engine to cancel, as those runs read the moment before. An id the engine has no run for returns an empty array and makes no cancel call, and an id that is not a uuid v7 throws before the engine is called at all. Both match on the engine's own run metadata, so a run in another namespace, or under another correlation id, is never touched. Cancelling a run that has already finished does nothing and raises nothing, so calling either twice is safe. With `outbox` (next paragraph) a call is not a no-op on the outbox side even when every run has finished or none exists: it still cancels the rows under that id the relay has not claimed.

Given the caller's own transaction — `kyu.runs.cancelForCorrelation(runId, { outbox: tx })` — both also cancel every outbox row the relay has not claimed yet, whether its `publish_at` is still ahead or has already passed: every row under that correlation id, or for `cancelForEnvelope` every row that envelope caused (its `causationId`), such as a workflow's hand-off continuation. The row gets `cancelled_at` and the relay never ships it. The engine cancel runs first; if it fails, no row is touched and the call throws. Two kinds of row can still reach the engine. The first is a row the relay claimed before the cancel's row update reached it and pushed to the engine after the cancel read the engine's runs — including a row held by a relay that stopped mid-push, which another relay ships once the claim goes stale. The run it starts is not in this call's engine cancel; a later cancel for the same id stops it. The second is a row whose push the engine took but the relay recorded as failed — its reply was lost, or the engine accepted only part of the batch. The relay counts the attempt and clears its claim, so the row is pending again: this cancel does cancel it, but its event is already in the engine. If the engine had not yet listed the run that event started when the cancel read the runs, that run is not in this call's engine cancel either; as for a claimed row, a later cancel for the same id stops it. The cancel also takes a row published under the same id earlier in the same transaction, so publish a message that must survive it, such as a cancellation notice, after the cancel call. It does not cover a row in any other database, nor a scheduled message looked up by its own id. If the caller's transaction rolls back after the engine cancel, the runs stay cancelled and the rows stay pending; call again. Cancelled rows are kept until your prune job deletes them (`pruneOutbox`, see Outbox retention above). Consumers must apply migration `20260924114140_outbox_cancelled_at.sql` first.

`cancelForEnvelope` reaches only the rows that envelope directly caused: after a second hand-off, the next continuation's `causationId` is the first continuation's own envelope id, not the original trigger's, so cancelling the original envelope misses it. `cancelForCorrelation` reaches every row under the correlation id regardless of how many hand-offs came before it, so it is the safer call for a workflow that may have handed off more than once.

### Tenant pause

`kyu.tenants.pause(db, tenantId)` holds one business tenant's new messages in the outbox: the relay stops claiming rows with that `tenant_id`, so nothing new for the tenant reaches the engine, while runs already there — running, parked in `sleepFor`/`waitFor`, or queued — carry on and finish. `kyu.tenants.resume(db, tenantId)` releases them; the relay ships them on its next tick in publish order, and `kyu.tenants.isPaused(db, tenantId)` reads the state. To drop a paused tenant's held rows instead of shipping them, cancel the tenant with `outbox` before resuming, as the `kyu.runs.cancelForTenant` paragraph below describes. `db` is your own pool or transaction, the database `publish()` writes to; pause and resume are safe to repeat, and a tenant id that is not a uuid throws before any query. `createPublisher({ source }).tenants` carries the same three calls, because none of them make an engine call, so a process that only holds a database connection — no `HATCHET_CLIENT_TOKEN` — can pause and resume too. A held message is not in the engine, so `scheduleTimeout` never fails it however long the pause lasts. On resume the backlog ships at relay speed and then queues like any burst, so size `scheduleTimeout` for that burst. A row the relay had already claimed when the pause committed still ships. Messages with no tenant are never held. A durable run that waits for a reply to a command it published while paused waits for the resume, and its `waitFor` timeout still runs. The relay's claim query scans past a paused tenant's held rows on every tick, so a pause held for a long time against a high-volume tenant grows that scan; this is for an operational hold measured in minutes to hours, not a standing per-tenant throttle. Engine rate limits cannot do this: see `docs/architecture/adr/20260924-tenant-pause-holds-messages-in-the-outbox.md`. Consumers must apply migration `20260924124242_paused_tenant.sql` first.

The pause is scoped to the producer database it runs against, not to the business tenant across the whole bus: `kyu_paused_tenant` lives in the caller's own database, and the relay reads it from that same database, so it holds only the rows that database's own outbox is holding. Any other service or project that also publishes for that business tenant id — from its own outbox, in its own database — keeps shipping normally. An operator who needs one business tenant held everywhere applies the pause in each producer's own database.

`kyu.runs.unsettledInNamespace({ since })` returns every run in this client's own namespace the engine still holds queued or running, and `kyu.runs.cancelUnsettledInNamespace({ since })` cancels them and returns how many the engine cancelled. Both need a `since`, because a namespace has no id to date itself from, and both list this namespace's own registered workflows first and name them in the engine call, so a run in another namespace is never read or cancelled. A run the list has shown queued or running for 60 seconds or more is left out when the engine's run detail says it completed or failed, at most 100 such runs checked per call. A run the engine lost track of while it was down — a durable run whose schedule timeout was never recorded — still reads queued, because nothing the engine exposes tells it from a live queued run; a cancel by id ended one on the local engine. A namespace with no registered workflow returns an empty array and makes no cancel call at all: an engine cancel filtered by an empty workflow list is not scoped to a namespace. In production, where a namespace is one company project's environment, `cancelUnsettledInNamespace` cancels every in-flight bus run for that whole project and environment, not one message or one workflow run — reach for it only as the operational broom the design document describes, never as an ordinary cancel. One `cancelUnsettledInNamespace` call is a request, not a settlement: a run the engine still holds when the call returns can stay unsettled for a while (observed on hosted CI and when the engine connection was lost, see `docs/proofs/2026-09-22-shop-failure-harness.md`), so a caller that must see the namespace empty repeats the cancel and polls `unsettledInNamespace` until it returns nothing.

`kyu.runs.unsettledForTenant(tenantId, { since })` and `kyu.runs.cancelForTenant(tenantId, { since })` do the same for one business tenant. They list this namespace's own registered workflows first and add the tenant id as a run metadata filter — `tenantId`, the key the relay copies from the envelope — so the engine reads or cancels only that tenant's runs in this namespace, never another tenant's and never another namespace's. `cancelForTenant` returns how many runs the engine cancelled. A tenant id that is not a uuid throws before the engine is called; a namespace with no registered workflow returns an empty array or 0 and sends no cancel. A message published with `tenantId: null` carries no tenant metadata and is never matched. Given the caller's transaction — `kyu.runs.cancelForTenant(tenantId, { since, outbox: tx })` — it also cancels that tenant's outbox rows the relay has not claimed, after the engine cancel, as `cancelForCorrelation` does; if the engine cancel fails, no row is touched and the call throws. That includes a paused tenant's held rows: they are cancelled, not shipped on resume, so pause, cancel with `outbox`, then resume releases only messages published after the cancel. It does not cancel a row the relay has already claimed, or rows in any other database. One `cancelForTenant` call is a request, not a settlement: a caller that must see the tenant empty repeats the cancel and polls `unsettledForTenant` until it returns nothing. It is not a pause: messages published for the tenant afterwards run as normal, so call `kyu.tenants.pause` first to stop new work.

A cancelled run ends as `cancelled`, not `failed`, and the engine does not retry it. A run parked in `sleepFor`/`waitFor` sees that wait reject as soon as the cancel reaches its worker — about 0.3 seconds on the local stack. Let the rejection propagate. A handler that is between two steps when the cancel arrives is not interrupted: JavaScript cannot stop a running body, so the handler finishes the step it is in and the engine drops the result. That is what keeps a cancel out of the middle of an `onceById` transaction. Do not try to tell a cancellation from an eviction inside a handler — the engine SDK aborts the same controller and raises the same `AbortError` for both, and an evicted run is one that will carry on somewhere else.

`worker.stop()` first refuses any new durable wait on that worker, then pauses the worker, evicts every parked durable run and waits for the bodies still running. A handler that reaches its first `sleepFor`/`waitFor` during the stop fails that attempt straight away and the engine retries it on whichever worker is available; `durable()` sets `retries` to 3 for this reason, and an explicit value still wins. The flag is one-way, so `createWorker` refuses a durable subscription object another worker already bound: build one subscription per worker.

`ctx.waitForChildren(replyDefinition, { where: { field, envelopeIds }, timeout })` waits for a whole set of child messages in one call. Publish the children the ordinary way first — `kyu.onceById(tx, runId, key, () => kyu.publish(tx, …))` inside your own transaction — then hand `waitForChildren` the envelope ids `publish()` returned. It registers one durable wait holding one condition per child, so the call returns as soon as every child has replied, or at `timeout`, whichever comes first. You get one outcome per child, in the order you gave the ids: `replied` with the decoded reply envelope, `failed` when the child never replied and the engine recorded a failed or cancelled run for it, or `pending` when the engine has no finished run for it yet. A failed child costs the full `timeout` before it is reported, because nothing pushes a reply for it. At most 50 children per call. A run parked here reads through `kyu.runs.forCorrelation` as an ordinary message wait — the reply definition's `name` with no `match` — because the registration holds one condition per child rather than one per-child label the durable log could carry back out.

`ctx.waitForAny([{ definition, where }, ...], { timeout, afterMessage })` parks on several message names in one wait and returns the first one that matches. Each entry names its own definition and its own `{ field, equals }` subject key, so a handler that needs two facts from two different events waits for either. The result says which entry woke it — `index` is its position in the list and `name` the message name — and carries that message's envelope, decoded with that entry's own definition. `afterMessage` applies to every entry, so the wake-check-park loop works here too and a message that already woke the handler never wakes it again through another entry. At most 10 entries per call. A run parked here reads through `kyu.runs.forCorrelation` as `{ kind: 'anyMessage', waits }`, one entry per name with the field match it is holding out for.

The handler body re-runs from the top on every replay, and `onceById` returns `{ ran: false }` the second time, so the handler must be able to find the ids it already published. Write them into your own ledger row in the same transaction as the publishes — [the shop example's `src/handlers/runWorkflow.ts`](https://github.com/kyuworks/shop-example/blob/main/src/handlers/runWorkflow.ts) records every step that way — or read them back with `SELECT id FROM kyu_outbox WHERE envelope->>'causationId' = $1 ORDER BY id` while the rows are younger than your prune job's retention (45 days by default); `id` is the envelope id, a uuid v7, so ordering by it is publish order, unlike `created_at`, which rows published in the same transaction can share. The child's reply is a message you define; it needs one field carrying the child's envelope id, and that field's dotted path is `where.field`.

A durable handler that must re-check a condition over its own data parks again after every wake: `waitFor` with the same `where`, and `afterMessage` set to the envelope the last wake returned. Envelope ids are uuid v7, so the wait matches only messages published after that one and the message that woke the handler never wakes it again. A message that lands while the handler is between the wake and the next park is still matched, because the lookback window covers it. The window is anchored at the run's start, not at each park — the engine memoises `now()` per run — so it grows with the run's age and never loses a message that lands between a wake and the next park. A message published before the last wake but delivered to the engine after it is not matched; the wait's `timeout` is the backstop, and the handler re-reads its own state on a timeout too. Each park is one durable wait, counted by its position in the run, so a restart replays the same sequence and re-runs no completed step.

Eviction of an already-parked run is the slow part: the engine SDK waits up to 30 seconds per run for the engine to acknowledge it, so size a supervisor's SIGTERM grace period above that — or pass `stopTimeoutMs` to `createWorker` to cap the whole stop.

A subscription declares a rate limit in product units: `rateLimit: { per: 'tenant', limit: 100, window: 'hour' }` starts at most 100 runs per business tenant per hour. `per` is `'tenant'` (the envelope's `tenantId`), `'correlation'` (its `correlationId`, so one workflow run and the commands it publishes share a count) or `'field'` with `field: 'data.leadId'` (a dotted path relative to the payload, as in `waitFor`'s `where.field`; a number counts by its text). `window` is `'second'`, `'minute'`, `'hour'`, `'day'`, `'week'`, `'month'` or `'year'`, `limit` is a whole number above zero, and each run counts as one; `subscribe()` and `durable()` throw a `KyuError` for anything else. The bucket is this subscription's own — its key starts with the client's namespace and the subscription name — so two subscriptions never share a count. To share one bucket across subscriptions, such as one provider quota, or to key on anything else, use the explicit form `rateLimits: [{ key: "'marketplace:' + additional_metadata.tenantId", limit: 50, period: 'minute' }]`; `rateLimit` resolves to exactly that declaration with its own key. A subscription sets one form, not both. `key` is a CEL expression over the event, the same language a concurrency key uses, so a constant such as `"'marketplace'"` gives every run one shared bucket and an expression over the tenant gives each business tenant its own. A run that would pass the limit is queued, not failed: it reads `queued` from `kyu.runs.forEnvelope` and starts in a later period. On the local stack a run held by a one-per-minute limit started 76 to 84 seconds after the run that used that period, because the engine re-checks held runs on its own tick. A key built from `additional_metadata.tenantId` only fits a message that always carries a business tenant: a global message has no `tenantId` in its metadata at all, so give those a constant key — a message published without a `tenantId` under such a key fails the run at once with `no such key: tenantId` and lands in the dead letter, it is not queued and the limit is not skipped. `per: 'tenant'` fails the same way, with `no such overload`, and `per: 'field'` fails at once with `no such key` when the payload lacks the field. `limit` must be a whole number above zero, and the SDK refuses anything else rather than letting the engine read it as a lookup of a static limit that was never registered. A held run is only safe while the hold is shorter than the subscription's `scheduleTimeout`: the engine checks that timeout when it next tries to schedule the run, so a run held past it is failed at that moment instead of started. On the local stack, a run held by a one-per-minute limit under a 10-second schedule timeout read `queued` for about 80 seconds and then `failed`, with no start time and no error message.

A subscription also declares how long a run may wait in the queue for a free slot: `scheduleTimeout: '30m'`. The engine's own default is 5 minutes and the SDK leaves it there — `subscribe()` and `durable()` send nothing when the caller sets nothing. A run that waits longer is failed without ever starting: it reads `failed` from `kyu.runs.forEnvelope` with no `startedAt` and no error message, which is how you tell a schedule timeout from a handler that threw, because a handler failure carries both a start time and an error text. That first dispatch also reads `attempts: 1`; a retry after a handler failure reads a higher attempt count, since it is a fresh dispatch under the same schedule timeout. It is the dead letter like any other failed run — alerted on and replayable — so nothing is lost, but under sustained overload every run that waits more than five minutes for a slot is dead-lettered instead of run. Size it above the deepest backlog you expect to clear: roughly the queue depth you are willing to wait through, times how long one run takes, divided by the slots serving it. Measured on the local stack with one slot and an 8-second handler, a 10-second schedule timeout failed the third of three events 10.4 seconds after it was created without starting it, and a 2-minute one ran all three. A zero or unreadable duration is refused before the engine, because `'0s'` fails every queued run in about 20 milliseconds with no error text anywhere. A parked durable run is not affected: the timeout covers only the wait before a run first starts, so a run evicted by `worker.stop()` and left unassigned for three times its schedule timeout still resumed on the next worker. A retry after a handler failure is a new dispatch too, so it re-enters the queue and waits under the same schedule timeout if a slot is busy: on the local stack, a retry queued behind a slot held 15 seconds under a 10-second schedule timeout failed without ever starting.

`kyu.worker(name, { subscriptions, serves })` registers only the subscriptions whose names are in `serves`, and leaves the rest for another process: one bus tenant, separate worker pools by subscription name. Build the whole subscription list once and start one process per pool, each naming what it serves, so a pool that calls a slow third party never holds up the pool that runs durable handlers. A name in `serves` that is not one of the subscriptions is a `KyuError` before the engine is called, as is an empty list — leave `serves` unset to serve them all. The one-subscriber-per-command check and the durable bind both see the served set only, so a subscription this worker does not serve stays free for the worker that does. A subscription no running worker serves gets no run at all: the engine does not back-fill when a worker starts later and picks it up, so every subscription must be served by some pool that is actually running.

`kyu.schedules.create({ name, cron, definition, data, tenantId })` registers a cron that publishes a message on a schedule; `remove` and `list` manage what is registered. A cron hangs off `kyu.scheduleRunner`'s workflow, which a worker must register before `create`, `remove` or `list` — call each only after `kyu.worker(...)` with `kyu.scheduleRunner({ db, definitions })` in its subscriptions has started, or the SDK throws a `KyuError` saying so instead of the engine's own bare "workflow not found". A cron's name is unique within this client's namespace, not across every consumer.

## Releasing

1. Open a PR that sets the same version in `packages/schemas/package.json`, `packages/sdk/package.json` and `packages/sdk/src/version.ts` (`check-package-versions.sh` fails the PR otherwise).
2. Merge it and wait for CI on `main` to pass. Check that the latest run of `newest-client.yml` is green too: it tests the newest Hatchet client the SDK's range lets a consumer install.
3. The CTO pushes tag `v<version>` on that commit. `release.yml` checks the tag is on `main`, that CI passed there, that the tag matches the version and that the tarballs are complete, then publishes both packages to npm with provenance. No token is involved: npm trusts this repository's `release.yml` (trusted publishing). If the run fails part way (schemas published, sdk not), re-run the workflow: `pnpm -r publish` skips a version already on the registry and publishes only what is missing.

### First release only (CTO)

1. Check the scope: `npm org ls kyuworks` lists you as owner; `npm view @kyuworks/sdk` and `npm view @kyuworks/schemas` return 404.
2. Reserve each name with a placeholder from your own machine, logged in with two-factor authentication: a folder holding only a `package.json` with the package name, version `0.0.1-reserved.0` and a description pointing at this repository, then `npm publish --access public --tag reserved`; then `npm deprecate <name>@0.0.1-reserved.0 "Placeholder. Use 0.1.0 or later."`. Do not store the login as a secret anywhere.
3. On npmjs.com, for each package: Settings, Trusted publishing, GitHub Actions; organisation `kyuworks`, repository `kyu`, workflow `release.yml`, no environment. Then Settings, Publishing access, "Require two-factor authentication and disallow tokens".
4. In this repository's settings add a tag ruleset for `v*` that only repository admins can create, update or delete.
5. Push tag `v0.1.0` on `main`.
